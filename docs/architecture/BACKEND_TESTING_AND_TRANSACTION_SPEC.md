# VANIGAR SANGAM — BACKEND TESTING & TRANSACTION SPECIFICATION

**Version:** 1.0.0  
**Phase:** Phase 3.6 — Service/Repository Transaction & Domain Operation Test Foundation  
**Status:** Approved Architectural Standard  

---

## 1. Overview & Testing Philosophy

This specification establishes the standardized testing conventions and transactional isolation patterns for the **Vanigar Sangam** backend architecture:
- Total test data isolation: automated tests must never mutate or delete persistent development data (including the provisioned `SUPER_ADMIN`).
- Zero database residue: tests that touch PostgreSQL must either roll back automatically or clean up their transient records with strict test-prefixed filters.
- Clear separation between fast in-memory unit tests and real PostgreSQL integration tests.
- Explicit validation of atomic rollback behavior for multi-step financial and audit operations.

---

## 2. Test Classification (Unit vs. Integration)

| Level | Scope | Dependencies | Primary Target |
| :--- | :--- | :--- | :--- |
| **Unit Tests** | Single class, function, or domain service | Zero external dependencies; uses `InMemoryRepository` or `createMockQueryable()` | Business logic validation, input validation, `AppError` mapping, calculation precision |
| **Repository Integration Tests** | Concrete repository methods against real PostgreSQL | Real PostgreSQL connection via `getDbPool()` or `runInTestTransaction()` | SQL query correctness, parameter binding, type mapping, constraint compliance |
| **Service Transaction Tests** | Cross-module operations, multi-entity transactions | Managed PostgreSQL transaction via `withTransaction()` or `runInTestTransaction()` | Transaction atomicity, rollback on failure, commit integrity, audit logging |
| **HTTP / Controller Integration Tests** | End-to-end request pipeline (`Request -> Validation -> Controller -> Service -> Response`) | Running API or in-memory Express `app` via `supertest` or HTTP client | Status codes, error envelopes, header handling, session cookies |

## 3. Transaction Testing Utilities & Isolation Patterns

The testing foundation in [`@vanigar/api/src/test-utils`](file:///c:/Users/Acer/OneDrive/Desktop/NNP@4%20maji/Web%20file/vanigar%20sangam%20for%20antigravity/apps/api/src/test-utils) provides three primary mechanisms:

### 3.1 Automatic Rollback with `runInTestTransaction`
For tests that insert or modify data in PostgreSQL, `runInTestTransaction` wraps the test body in a transaction and automatically rolls it back upon completion:

```typescript
import { runInTestTransaction } from '../test-utils/index.js';

await runInTestTransaction(async (client) => {
  // All DDL/DML executed on client is visible within this block...
  await client.query('INSERT INTO ...');
  
  // ...and automatically rolled back when the block exits!
});
```
*Benefits:* 100% database cleanup with zero residue and zero risk to persistent development records.

### 3.2 Explicit Commit with `withTransaction`
When testing that a service or repository actually commits data to the database, use `withTransaction`, ensure test IDs use an approved test prefix, and clean up in a `finally` block:

```typescript
import { withTransaction } from '../database/index.js';
import { createTestIdentifier, cleanupTestRecords } from '../test-utils/index.js';

const testUsername = createTestIdentifier('commit_test');
try {
  await withTransaction(async (client) => {
    // Perform operations...
  });
  // Verify persistence from pool...
} finally {
  await cleanupTestRecords('admin_users', 'username', `${testUsername}%`);
}
```

### 3.3 Test Identifier Conventions
All test records must use a unique identifier generated by `createTestIdentifier(prefix)`.  
Format: `__test_${prefix}_${timestamp}_${nonce}__`  
*Invariant:* Cleanup routines refuse to run unless the target pattern matches an approved test prefix (`__test_`, `test_`, `__tx_`, `__repo_`, `__coord_`).

## 4. Repository Testing Conventions

1. **Dual-Executor Support:** Every repository extends `BaseRepository` and must accept an optional `executor?: Queryable` parameter on all read and write methods.
2. **Transactional Route Verification:** Tests must verify that when an explicit `Queryable` client is provided, the repository queries using that client and observes uncommitted changes within that transaction.
3. **Missing Resource Handling:** Repositories must return `null` (not throw) when `findById` or `findByUsername` finds no record.
4. **Safe Existence Checks:** Use `existsBy...()` returning a boolean (`SELECT 1 ...`).

---

## 5. Service-Layer Testing Conventions

1. **Decoupling from Express:** Domain services must **never** import Express `Request`, `Response`, or `NextFunction`. Input is passed as typed DTOs, and context is passed via `ServiceContext`.
2. **Typed Application Errors:** Services must communicate operational failures by throwing typed subclasses of `AppError`:
   - `NotFoundError` (404, `code: 'NOT_FOUND'`)
   - `ValidationError` (400, `code: 'INVALID_INPUT'`)
   - `BadRequestError` (400, `code: 'BAD_REQUEST'`)
   - `ConflictError` (409, `code: 'CONFLICT'`)
   - `ForbiddenError` (403, `code: 'FORBIDDEN'`)
   - `UnauthorizedError` (401, `code: 'UNAUTHENTICATED'`)
3. **Internal Error Masking:** Low-level database errors (e.g. connection drops, syntax failures) must never leak database details to callers; services must wrap unexpected failures in a sanitized `InternalError` (500, `code: 'INTERNAL_ERROR'`).
4. **Mock Repositories:** For unit testing complex service workflows, use `InMemoryRepository<T>` or `createMockQueryable()` to run hundreds of test cases in milliseconds without database I/O.

## 6. Future Financial & Multi-Entity Atomicity Testing

When implementing Phase 4+ business modules (Members, Daily Sheet, Collections, Loans, Cash), tests must verify:

1. **Multi-Entity Commit Atomicity:**  
   e.g., Recording a loan repayment must atomically:
   - Decrement member loan balance (`BIGINT` paise).
   - Insert repayment ledger entry (`BIGINT` paise).
   - Increment cash on hand (`BIGINT` paise).
   - Write audit log record.  
   The test must verify all 4 records exist upon commit.
2. **Partial Failure Rollback:**  
   Simulate a failure on step 3 or 4 (e.g., constraint violation or mock error). Verify that **none** of the records from steps 1, 2, 3, or 4 persist in the database.
3. **Exact Integer Arithmetic:**  
   Verify that financial calculations use `BigInt` paise (`safeAddPaise`, `safeSubtractPaise`) and zero floating-point drift occurs.

## 7. Prohibited Test Practices

| Prohibited Practice | Danger / Violation | Required Alternative |
| :--- | :--- | :--- |
| `TRUNCATE table` or `DELETE FROM table` without WHERE clause | Destroys development administrator accounts and migration metadata | Target only test-prefixed rows (`WHERE username LIKE '__test_%'`) |
| Hardcoded test IDs without timestamp/nonce | Concurrent test runs collide or fail on unique constraints | Use `createTestIdentifier(prefix)` |
| Committing test records without a `finally` cleanup block | Pollutes the database with lingering test artifacts | Use `runInTestTransaction` (auto-rollback) or `finally { cleanupTestRecords(...) }` |
| Coupling services to Express `req`/`res` | Prevents services from being used in CLI commands, background jobs, or unit tests | Pass typed DTOs and `ServiceContext` |
| Asserting on raw SQL error strings | Leaks database internals and breaks if error wording changes | Assert on `AppError` code (`INVALID_INPUT`, `NOT_FOUND`, etc.) |
