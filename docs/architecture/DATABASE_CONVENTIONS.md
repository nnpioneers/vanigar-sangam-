# VANIGAR SANGAM — DATABASE SCHEMA & MIGRATION CONVENTIONS

**Version:** 1.0.0  
**Phase:** Phase 3.2 — Database Schema & Migration Conventions Foundation  
**Status:** Approved Architectural Standard  
**Database Engine:** PostgreSQL 18  

---

## 1. Overview & Objective

This document defines the mandatory database conventions, schema design standards, and migration practices for the **Vanigar Sangam** system. All upcoming business modules (Members, Daily Sheet, Collections, Loans, Guarantors, Cash Operations, Reports, and Audit) must strictly adhere to these conventions.

---

## 2. Migration Architecture & Conventions

### 2.1 File Naming & Numbering
- **Directory:** `database/migrations/`
- **Naming Pattern:** `NNN_description_in_snake_case.sql`
- **Rules:**
  1. Prefix must be a **3-digit zero-padded integer** starting from `001` (e.g., `001_init_schema_migrations.sql`, `002_create_admin_users_and_sessions.sql`).
  2. Numbers must increment sequentially without gaps.
  3. Description must be in lower snake_case explaining the purpose of the migration.
  4. Migrations are **forward-only**; never modify an already-executed migration.

### 2.2 Execution & Idempotency
- **Runner:** Custom native `pg` migration runner (`apps/api/src/database/migrator.ts`).
- **Tracking Table:** `schema_migrations` (`id`, `name`, `executed_at`, `execution_time_ms`).
- **Transaction Safety:** Every migration file executes inside an isolated transaction (`BEGIN` ... `COMMIT`). If any statement fails, the entire migration is rolled back (`ROLLBACK`) and execution halts immediately.
- **DDL Idempotency:** Use `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, and safe alter statements where applicable.

## 3. Schema & Identifier Conventions

### 3.1 Naming Conventions
- **Schema:** Default PostgreSQL `public` schema.
- **Table Names:** Plural, lowercase snake_case (e.g., `admin_users`, `sessions`, `members`, `daily_sheets`, `daily_collections`, `loans`, `cash_holdings`, `audit_logs`).
- **Column Names:** Singular, lowercase snake_case (e.g., `id`, `username`, `full_name`, `sheet_date`, `created_at`).
- **Constraint Names:** Explicit, descriptive names:
  - Primary Key: `{table}_pkey`
  - Unique: `uq_{table}_{columns}`
  - Foreign Key: `fk_{table}_{referenced_table}`
  - Check: `chk_{table}_{rule}`

### 3.2 Primary Key (PK) Conventions
| Table Category | PK Data Type | Generation Strategy | Example |
| :--- | :--- | :--- | :--- |
| **Business Entities** | `UUID` | `DEFAULT gen_random_uuid()` | `members.id`, `loans.id`, `daily_sheets.id` |
| **Session / Token Store** | `VARCHAR(128)` | Cryptographic hex token generated by backend | `sessions.id` |
| **High-Volume Ledgers / Logs** | `BIGINT` or `UUID` | `GENERATED ALWAYS AS IDENTITY` or `DEFAULT gen_random_uuid()` | `audit_logs.id`, `schema_migrations.id` |

## 4. Column Data Types & Conventions

### 4.1 Temporal Values: Dates vs. Timestamps
- **Business Calendar Dates (`DATE`):**
  - Use `DATE` for all calendar dates that have no time-of-day component:
    - `sheet_date` (collection day)
    - `start_date`, `due_date` (loan term dates)
    - `repayment_date` (ledger transaction date)
  - *Never* use `TIMESTAMPTZ` for calendar dates. This avoids timezone conversion shifts across midnight.
- **Audit & System Timestamps (`TIMESTAMPTZ`):**
  - Use `TIMESTAMPTZ NOT NULL DEFAULT NOW()` for all real-world event occurrences:
    - `created_at`, `updated_at`
    - `executed_at`, `last_activity_at`, `expires_at`
    - `closed_at`, `transferred_at`, `confirmed_at`

### 4.2 Monetary Values & Arithmetic Precision
Financial operations require strict precision. To eliminate IEEE 754 floating-point inaccuracies (`0.1 + 0.2 = 0.30000000000000004`):
1. **PostgreSQL Column Types:**
   - Use `NUMERIC(12, 2)` or `BIGINT` (representing integer paise: ₹1 = 100 paise).
   - In both cases, enforce `CHECK (amount >= 0)` (or `> 0` for non-zero transactions).
2. **TypeScript Application Layer:**
   - Use integer paise (`bigint` or integer `number`) for internal additions, rollups, and settlement order calculations.
   - Use standardized conversion helpers (`toPaise`, `toRupees`, `formatRupees`) in `apps/api/src/database/money.ts`.
   - Never perform arithmetic directly on floating-point rupee values.

### 4.3 Enumerations & Status Codes
- Represent statuses as `VARCHAR(20) NOT NULL` with explicit `CHECK` constraints:
  ```sql
  status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE' 
    CHECK (status IN ('ACTIVE', 'INACTIVE', 'SUSPENDED'))
  ```
- **Rationale:** Native PostgreSQL `ENUM` types complicate column alterations and migrations. `VARCHAR` with `CHECK` constraints provides identical validation guarantees while remaining migration-friendly.

## 5. Foreign Key & Indexing Conventions

### 5.1 Foreign Key (FK) Referential Actions
- **Ephemeral / Child Records:**
  - `ON DELETE CASCADE` is permitted ONLY for child records that have no independent lifecycle or financial significance (e.g., `sessions.admin_id -> admin_users.id`).
- **Financial / Ledger / Audit Records:**
  - Strictly `ON DELETE RESTRICT` (or default no-action).
  - Financial records (Collections, Repayments, Loans, Cash Transfers, Audit Logs) must **never** be cascade-deleted. If a parent record is removed or archived, foreign key constraints must actively block deletion.

### 5.2 Mandatory Indexing Rules
1. **Every Foreign Key:** Must have an index: `CREATE INDEX idx_{table}_{fk_column} ON {table}({fk_column});`
   - Prevents full-table scans during relational JOINs and parent table constraint checks.
2. **Search / Filter Columns:** High-cardinality lookups, status filters, and expiration scans must be indexed:
   - Example: `CREATE INDEX idx_sessions_expires_at ON sessions(expires_at);`
   - Example: `CREATE INDEX idx_loans_status ON loans(status);`

## 6. Financial Ledger & Audit Immutability

1. **Append-Only Principle:**
   - Financial ledger entries (`daily_collections`, `loan_repayments`, `cash_transfers`, `audit_logs`) are append-only.
   - Direct `UPDATE` or `DELETE` on finalized financial rows is prohibited.
   - Adjustments or corrections must be recorded as separate compensating entries with cross-references to the original transaction ID.
2. **Audit Logging:**
   - Every state-altering action records: `actor_type`, `actor_id`, `action`, `entity_type`, `entity_id`, `old_values`, `new_values`, and `created_at`.
